# QA/QC testing report — format specification

Reverse-engineered from the single exemplar:
`C:\Users\po.nienchen\OneDrive - priorpartners.com\Documents\05_Code_Scripts\tool_development\Masterplan_Plus\urban_intelligence\qa\reports\qa_report_260809_7.html`
(849 lines, whole file read — beginning, full middle structure, and footer all inspected directly, no sampling gaps).

This is declared the canonical style for all future "QA/QC testing report" documents. A future
author with only this spec (no access to the exemplar) should be able to produce a new report
judged same-format.

---

## 1. Document purpose / genre

A **machine-generated, single-file HTML test report** for a software build ("Urban Intelligence"
plugin stream on top of a "company platform" dashboard product). It is generated by a script
(`qa\run_qa.py`, named in the footer) that runs a suite of **gates** (automated test functions,
each with a stable snake_case id) and pastes their live console output plus structured
assertion tables into the page. It is explicitly **evidentiary, not promotional** — the page
itself states its own editorial intent: *"this page is evidence, not advertising: failures
render red."* Content recorded per gate: pass/fail verdict, individual assertion rows with
numeric evidence, raw transcript log excerpts, provenance/engine/licence metadata, payload-size
budgets, and (uniquely) narrative **adversarial-review verdicts** from a second role ("geoai_critic")
that re-audits the outputs and records what it found wrong and how it was fixed. There is no
"environment" block (OS/browser/versions) and no author/reviewer sign-off names — provenance is
carried per-analysis (engine name+version, CRS, source licence, generation timestamp) rather than
per-document.

## 2. Full visual token set

Everything is inline in one `<style>` block in `<head>` — **no external CSS or JS, no `<script>`
tags anywhere in the body**. Single quotes are used for all HTML attributes throughout
(`<html lang='en-GB'>`, `class='chip pass'`, etc.) — treat this as a house convention.

### Base typography and layout

- `*{margin:0;padding:0;box-sizing:border-box}` — full reset.
- `body{background:var(--bg);color:var(--text);font-family:var(--sans);font-weight:300;
  padding:40px 56px;max-width:1400px;margin:0 auto}` — light (300) body weight throughout,
  centred column, generous side padding, no responsive breakpoints defined (fixed max-width).
- `h1{color:var(--strong);font-weight:500;font-size:34px;margin:6px 0 4px}`
- `h2{color:var(--strong);font-weight:500;font-size:22px;margin:36px 0 10px;
  border-top:1px solid var(--line);padding-top:18px}` — h2 doubles as a section-divider rule.
- `h3{color:var(--strong);font-weight:500;font-size:16px;margin:16px 0 8px}`
- Font stack is entirely GT America (P+P's house typeface) for both display and mono roles,
  falling back to Arial/Consolas — consistent with the firm's brand font rule even though the
  colour palette departs from the official light/cream template (see §9).

## 3. Page anatomy, in document order

1. `<!doctype html><html lang='en-GB'><head>` — meta charset utf-8, `<title>QA report — {D Month YYYY}</title>`, then the single inline `<style>` block. No favicon, no external resources of any kind.
2. **Kicker** — `<div class='kick'>{Stream name} · QA report</div>` (e.g. "Urban intelligence · QA report"). Mono, uppercase, letter-spaced, kicker-orange.
3. **Title** — `<h1>QA run — {D Month YYYY}</h1>` (em dash separator; day has no leading zero).
4. **Meta line** — `<div class='meta'>` — one line, middot-separated (` · `) clauses: phases covered (`phases: ui0, ui1, ...`), the project/stream label, where full transcripts live, and a closing editorial disclaimer sentence. This is the ONLY "environment"-like metadata block — there is no separate table of OS/versions/browser.
5. **`<h2>Green-light requirements</h2>`** — the acceptance-criteria section, one `<h3>` sub-section per project **phase** (id pattern `{STREAM}-{N} — {phase name}`, e.g. "UI-0 — foundations"), each phase heading carrying an overall status chip (`GREEN` text inside `chip pass`). Under each phase heading, a `<table class='req'>` (icon | Requirement prose | Gates — where "Gates" cell lists one-or-more gate-id chips that back that requirement).
6. **`<h2>Gate results, this run</h2>`** — the closest thing to a summary dashboard: a single `<div class='chips'>` flex-wrap strip listing EVERY gate id in the run as its own coloured chip. This is a taxonomy strip, not a numeric tile (see §4 — no pass-count tile exists).
7. **Repeating gate sections** (the bulk of the document) — one per gate, in the same order as the chips strip; see §5 for the full repeating-unit anatomy.
8. **`<h2>geoai_critic verdicts</h2>`** — the sign-off section; one `<h3>` + `<div class='verdict'>` pair per reviewed phase. See §6.
9. **Footer** — `<div class='foot'>` single line, closes `</body></html>`.

No table of contents / anchor navigation exists anywhere (headings carry no `id` attributes and
there are no in-page jump links). No collapsible/`<details>` sections — the whole thing is one
long static scroll.

## 4. Recurring components and exact styling

- **Result tables** — two flavours: (a) the plain 3-column assertion table used inside every
  gate section (icon | Assertion | Detail, `Detail` cells use `td.mono` so evidence numbers
  render in monospace white against grey prose); (b) `.req` requirement tables in §3.5 (same
  shape, narrower/larger icon column). Card tables (inside `.card`) drop the header row entirely
  and are 2-column key/mono-value only.
- **Pass/fail/skip badges ("chips")** — outline-only (no fill), uppercase, letter-spaced mono
  11px, 1px border. Exact colours: pass = `#4ade80` text on `rgba(74,222,128,.5)` border; fail =
  `#f87171` text on `rgba(248,113,113,.6)` border; not_built/not_run = `#5f5f5f` text on the
  generic hairline border colour. No distinct "skip"/"warn" chip variant exists despite `--warn`
  being defined — if a future report needs skip/warn states, extend the pattern
  (`.chip.skip{color:var(--warn);border-color:rgba(245,158,11,.5)}`) rather than inventing new
  hues.
- **Code/log blocks** — `<pre>` tail-excerpts of the underlying test runner's live stdout,
  reproducing an indented pytest-like format: numbered sub-step headers (`  2 - description`),
  `    ok    assertion text - evidence`) lines, blank line, then a single closing verdict line
  in the exact form **`PASS  {one-sentence plain-English summary of what was proven}.`** (infer
  `FAIL` uses the same template). This closing sentence is the human-readable "so what" and is
  distinct from the structured table above it — the table is the machine checklist, the `<pre>`
  tail is the narrated proof.
- **Evidence figures** — `.figs` is a responsive grid (`auto-fill, minmax(320px,1fr)`) of
  `<figure>` cards, each a bordered/surfaced box containing one `<img>` and a mono, dim,
  small-caption `<figcaption>` describing what the image proves. **Images are NOT base64-embedded
  data URIs** — they are plain `<img src='img_260809_7/{gate}_{name}.png'>` relative references
  to PNG files in a sibling folder. This makes the HTML file itself much smaller than a
  self-contained report would be and means the report is NOT portable as a single file — it
  depends on its sibling `img_{date}_{n}/` folder existing alongside it.
- **Payload/budget bars** — `.bar` is a bordered, surfaced horizontal meter (fixed 22px height,
  max-width 640px): a `.fill` div with `width:NN%` inline style (blue `--accent` fill at .75
  opacity, or `.fill.over` in `--bad` red when a ceiling is exceeded) and an absolutely-positioned
  mono label span reading `{name}: {used} / {ceiling} bytes`. Used only in the payload_budget
  gate section in this exemplar, but the pattern generalises to any bounded-quantity check.
- **Cards** (`.card`) — a bordered (thistle `--ui` colour), surfaced box used for supplementary
  structured evidence that doesn't fit the assertion-table shape: provenance blocks (title,
  engine+version, CRS, edge buffer, sources, generated timestamp), band-summary tables,
  "zero-delta proof" tables, licence-audit tables, preset-build matrices. Card heading is an
  `<h3>` coloured thistle, margin-top removed so it sits flush against the card's top border.
- **Severity markers** — there is NO structured severity badge/component. Severity ("N major,
  M minor findings") appears only as free prose inside `.verdict` paragraphs (see §6) — treat
  severity as narrative, not a first-class visual element, unless extending the format.
- **Transcript link** — every gate section closes with `<div class='meta'>` containing a single
  `<a href='../transcripts/{date}_{gate_id}.txt'>full transcript</a>` link. Note the transcript
  filename carries only the date, NOT the run-sequence suffix that the image folder carries (see
  §8) — inferred convention: transcripts are overwritten per gate on each run of that date and
  always reflect the latest run, while image folders are kept per numbered run so screenshots
  from superseded runs aren't silently overwritten.

## 5. The repeating unit — a single gate/test entry

This is the heart of the format. Each gate renders, in fixed order:

1. `<h3>{gate_id} <span class='chip {pass|fail}'>{pass|fail}</span></h3>` — gate id is the exact
   snake_case identifier used everywhere else (chips strip, requirement-table "Gates" cells,
   transcript filename, verdict section id).
2. **Assertion table** (`<table>`, no class) — header row `<th></th><th>Assertion</th><th>Detail</th>`;
   one body row per individual check: `<td><span class="ok">&#10004;</span></td>` icon cell,
   `<td>{plain-English assertion, phrased as a claim already proven true}</td>`,
   `<td class='mono'>{numeric/string evidence, or empty if the assertion is self-evidently binary}</td>`.
   Assertions read as completed claims ("centre Choice exceeds corner Choice (radius 800)"), not
   as instructions or test names — write new entries the same way.
3. *(optional, 0–2 per gate)* One or more `<div class='card'>` evidence blocks — for provenance,
   band tables, hashes, or other structured detail too shaped to fit the assertion table.
4. *(optional)* One `<div class='figs'>` grid of evidence screenshots/plots, each captioned.
5. *(optional, payload_budget only in this exemplar)* One or more `<div class='bar'>` meters.
6. **`<pre>` transcript tail** — last ~10–20 lines of the gate's actual console run, ending in
   the `PASS  {summary sentence}.` line described in §4.
7. **`<div class='meta'>` transcript link** — closes the section.

Gate sections are NOT wrapped in any container element (no `<section>`, no id) — they are simply
sequential `<h3>...</h3>` + siblings at the body level, one after another.

## 6. Overall verdict / sign-off

There is no single document-level "APPROVED / REJECTED" stamp. Sign-off is distributed as
**per-phase adversarial-review verdicts** under `<h2>geoai_critic verdicts</h2>`, one per phase
that was reviewed:

```html
<h3>{gate_id_for_the_verdict} <span class='chip pass'>acceptable</span></h3>
<div class='verdict'>{prose}</div>
```

`.verdict` is a thistle-left-ruled, dim, 14px, max-width-900px prose block (NOT a table). The
prose follows a consistent internal template, evidenced across all 5 verdicts in the exemplar:

> `{PHASE-ID} ({short phase name}): VERDICT {acceptable|not acceptable}, {date}, after {N}
> adversarial round(s)[, plus re-verification].` then a narration of each round — what was
> initially wrong (counted as "N major, M minor findings" with a parenthetical list), what was
> fixed, and **how the critic independently re-verified** the fix (re-running gates live,
> reproducing pipelines from scratch, independent recomputation) — closing with any **open
> ledger items** that don't block sign-off but are disclosed for the record.

Only two verdict outcomes appear in the chip: `acceptable` (styled `chip pass`) — infer
`not acceptable` would use `chip fail`. There is no numeric score, star rating, or percentage —
sign-off is a categorical verdict plus a fully narrated justification.

## 7. Writing conventions

- **British English** throughout: "licence" (noun spelling), "normalised", "colour"-family
  spellings not directly attested but consistent with house style elsewhere in the workspace.
- **Sentence case** for all headings and labels ("Green-light requirements", "Gate results, this
  run", "Merged plugin fragment") — only the first word and proper nouns/ids are capitalised.
- **Date format**: `D Month YYYY` (e.g. "9 August 2026") — day has NO leading zero, unlike the
  brand doctrine's `DD Month YYYY`; note this discrepancy explicitly if strict brand compliance
  is later required.
- Numbers use comma thousands separators (`22,275`, `1,194,727`) and are usually paired with
  their unit/context in the same cell rather than a bare number.
- **Em dash** ( — ) is used as the standard clause separator in headings and prose (title, phase
  names, meta line clauses). **Middot** ( · ) separates short parallel items on one line (kicker,
  meta line, footer, provenance strings). Do not mix these roles.
- **Two id/numbering schemes observed**:
  - Phase ids: `{STREAM_PREFIX}-{N}` where N is 0-indexed (`UI-0` … `UI-6`), each followed by an
    em-dash and a short lowercase descriptive name.
  - Gate ids: snake_case, no numbering, human-readable but code-identifier-shaped
    (`ssx_known_answer`, `atlas_heights`, `probe_ui`) — these are literal Python test/gate
    function names surfaced verbatim, not authored prose.
- Assertions and verdict prose favour a plain-spoken, slightly informal-technical register
  ("nothing inherited", "damage is local", "the browser sums nothing") over corporate report
  language — carry this voice forward rather than genericising it.
- **KNOWN DEFECT in the exemplar, do not imitate**: several `<pre>` blocks contain a literal
  `�` replacement character where an em dash or apostrophe should be (e.g. "PASS the company
  platform builds identically ... � the hook is provably inert"). This is a mojibake artifact
  from how the report generator captured subprocess stdout (likely a cp1252/utf-8 mismatch),
  visible only inside `<pre>` blocks, not in the surrounding structured HTML text (which
  correctly uses `&#x27;`/literal em dashes). Treat this as a bug in the exemplar's generator,
  not a format convention — new reports should encode `<pre>` content as clean UTF-8.

## 8. File naming convention (inferred)

Filename: `qa_report_260809_7.html` → pattern `qa_report_{YYMMDD}_{N}.html`, where `YYMMDD` is
the run date with no separators (matches `260809` = 9 August 2026, and matches the date-stamp
convention used elsewhere in the exemplar's own text, e.g. restore point `_restore_260808_...`)
and `{N}` is inferred to be a **same-day run/sequence number** (this is the 7th run of the day,
or the 7th surviving report — cannot be fully disambiguated from a single exemplar). Supporting
evidence for the sequence-number reading: the sibling image folder is named `img_260809_7/`
(carrying the SAME `_7` suffix as the report filename), while transcript files referenced from
inside the report are named only `260809_{gate_id}.txt` (date only, no `_7`) — i.e. transcripts
are shared/overwritten across same-day reruns, but each report+image-folder pair is uniquely
numbered so a specific run's screenshots are never overwritten by a later rerun on the same day.
**A future report should be saved as `qa_report_{YYMMDD}_{N}.html` alongside a matching
`img_{YYMMDD}_{N}/` folder for its figures, in the same directory as this exemplar
(`.../qa/reports/`), with transcripts in the sibling `.../qa/transcripts/` folder named
`{YYMMDD}_{gate_id}.txt`.**

## 9. Distinctive / brand-recognisable elements

- **Prior + Partners orange, `FF511D`**, appears exactly once as a design token (`--kicker`) and
  is used ONLY for the small eyebrow/kicker label at the very top of the page. This is the one
  deliberate brand tie-in.
- Everything else departs from the official P+P light/cream house template: this report is a
  **dark-mode, near-black, engineering/terminal-styled** document (`#0a0a0a` background, light
  grey body text, GT America Mono for all data/evidence), not the Orange/Aubergine/Cream/Black
  light template used for client-facing decks and documents. Treat this QA report style as a
  **separate, internal-tooling sub-brand** that borrows only the kicker-orange accent and the
  house typeface (GT America) from the main P+P standard — it is explicitly NOT meant to leave
  the building in this form (footer literally says "PNC · personal R&D").
  Do not apply the full Orange/Aubergine/Cream/Black P+P palette here; that rule governs
  external-facing deliverables, and this format is self-evidently an internal one.
- The accent/link colour is a distinct, non-brand blue (`#005DFF`), and there's a secondary
  "Thistle" purple (`#C8B5E2`) used for card/verdict framing that the report's own body text
  names explicitly as a stream's registry colour — i.e. the palette has a functional/systems
  meaning (each plugin "stream" may carry its own accent colour) beyond pure decoration, though
  only Thistle is evidenced in this single exemplar.
- Footer format: `{owner} · {classification} · {project} | QA report | {date} | generated by
  {script path}` — e.g. `PNC · personal R&D · urban intelligence | QA report | 9 August 2026 |
  generated by qa\run_qa.py`. Note the mixed separators (middots within the owner/classification/
  project clause, pipes between the outer fields) — reproduce exactly, not just "some separator".

## Explicit absences (format does NOT include)

- No table of contents / anchor navigation.
- No numeric pass-count summary tile ("47/50 passed", percentage, or progress ring) — the
  "dashboard" is a flat strip of named, individually-coloured gate chips, not aggregate stats.
- No collapsible/expandable sections (`<details>`), no JavaScript at all.
- No embedded (base64) images — all figures are external relative file references; the report is
  NOT a single portable file, it depends on sibling `img_*/` and `transcripts/` folders.
- No environment/versions table (OS, browser, dependency versions) as a distinct block — such
  detail, where present, is folded into per-gate "engine" provenance cards instead.
- No structured severity badges (critical/major/minor) — severity is narrative prose only, inside
  `.verdict` blocks.
- No named human reviewer/signatory — sign-off is attributed to a role (`geoai_critic`) and a
  gate id, not a person, and the only person mentioned is the initials "PNC" in the footer/meta
  as stream owner, not as an approver.
- No `warn`/`skip` chip variant is actually used, despite the `--warn` colour token existing in
  the palette (dead/reserved token in this exemplar).
